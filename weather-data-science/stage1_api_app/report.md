# stage1_api_app 成果報告

## 應用情境

「天氣速報小幫手」：輸入城市 slug,輸出今明兩天天氣預報＋一段穿搭/出行
建議。情境設定是一般民眾早上出門前想快速知道「要不要帶傘、要穿什麼」,
不需要自己解讀一堆氣象數字。

## 系統組成

| 元件 | 角色 | 是否為真實外部服務 |
|---|---|---|
| Open-Meteo forecast API | 提供未來兩天天氣預報 | 是（免帳號免金鑰,CC BY 4.0） |
| `mock_ai_server.py`（本地,port 8331） | 依天氣數字生成建議文字 | 否——規則式邏輯,模仿 OpenAI 格式 |
| `weather_brief.py`（CLI） | 串接以上兩者並排版輸出 | — |

### 即時模式（去掉 `--offline`，2026-07-24 00:26 前後實測，台中）

即時打 Open-Meteo forecast API 拿到的回應與離線樣本結構一致,唯數字不同
（多雲、16% 降雨機率、25.1~31.5 度）——證明即時/離線兩條路徑走的是同一套
格式化邏輯,不是各寫一份。

### 錯誤處理實測

關掉 mock AI 服務後重跑,CLI 沒有丟出未捕捉例外,而是印出：

```
(AI 建議服務目前無法連線：HTTPConnectionPool(host='127.0.0.1', port=8331):
Max retries exceeded with url: /v1/chat/completions ... Connection refused;
請確認 mock_ai_server 是否已啟動於 http://127.0.0.1:8331，...)
```

天氣預報部分（今天/明天段落）仍正常顯示——驗證了「AI 服務掛掉不影響
天氣資料顯示」這個設計目標。

## 測試結果

`venv/bin/python -m pytest tests/test_stage1_api_app.py -v`：**20 passed**
（2026-07-24 實測，3 個 StarletteDeprecationWarning，不影響測試結果）。

測試涵蓋：天氣代碼對照（含未知代碼防呆）、prompt 格式與 mock 服務正規
表示式的契約、離線樣本讀取、`fetch_forecast` 的重試/最終失敗兩條路徑、
`generate_advice` 四種規則分支（高降雨機率/高溫/強風/看不懂格式）、mock
服務的 401（缺 Authorization / 金鑰錯誤）與 200（含 OpenAI 相容欄位）、
`main()` 的優雅降級路徑。

## 誠實結論

- mock AI 服務是純規則引擎,不是機器學習模型,也不是真的大型語言模型——
  這件事在 README、程式碼 docstring、CLI 輸出的段落標題（「本地 mock
  服務規則式生成，非真實 LLM」）都重複標示,避免學員誤以為串接了真的 AI。
- 建議文字的品質上限就是規則涵蓋的情境：目前只處理降雨機率、溫度、風速
  三個維度,遇到格式不符的輸入會誠實回報「看不懂」,不會硬掰一個聽起來
  合理但其實沒讀懂輸入的回覆。
- 本課程沒有實際串接任何付費 AI 服務（沒有申請 OpenAI 帳號、沒有花任何
  金額）,`mock_ai_server.py` 的存在就是為了讓這件事在完全零成本、零帳號
  的前提下也能練到格式與架構。
