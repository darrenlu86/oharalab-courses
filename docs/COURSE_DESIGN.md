> 回上層：[課程總覽 README](../README.md)
>
> 給帶課老師／進階學員看的文件：說明「為什麼六個階段要這樣切」「每個階段教什麼、刻意不教什麼」「怎麼帶課、怎麼驗收」。學員如果只是想動手做，直接看各階段 README 即可，不必先讀這份文件。

## 1. 設計理念：為什麼用「同一個電商」貫穿六個階段

課程選定「沖沖咖啡 BrewGo」這個虛構品牌，用同一套商品型錄（12 筆商品）、同一套品牌視覺語言（色彩／字體 tokens），從一頁式活動頁一路做到含即時推播與壓測報告的完整平台。這個設計有三個理由：

1. **對照真實接案的成長路徑**：真實世界裡，一個小型商業網站很少一開始就是完整的前後台系統——通常是先有一個活動頁或形象網站，隨著業務成長才逐步加上型錄、購物車、後端、後台管理、最後才是效能與擴容。六階段的順序刻意模擬這個真實的成長路徑，而不是照技術難度隨機排列。
2. **概念可遷移**：同一個商品型錄、同一組品牌視覺，代表學員在 stage2 學到的「共用元件」概念，到了 stage3 換個做法（React 元件）解決的是同一類問題；stage4 的「購物車」不是全新的功能，而是 stage3 已經做過一次、這次換成伺服器端實作。學員不必每階段重新理解「這是什麼系統、賣什麼東西」，可以把全部注意力放在「這個階段新增的技術概念」上。
3. **每階段可對照前後差異**：因為商品資料、視覺語言不變，學員可以直接比較「同一支購物車功能，stage3 怎麼做、stage4 怎麼做」，這個對照本身就是最直接的教材——每階段 README 的「與上一階段的差異」一節就是刻意設計成拿前一階段的實際程式碼／檔案路徑當對照組，不是憑空描述新技術。

## 2. 六階段切分邏輯

以下每節依序列出：教學目標、上一階段的痛點入口、本階段新概念清單、刻意不教什麼（留給哪一階段）。

### Stage 1 — 一頁式靜態網頁（WEB-13）

- **教學目標**：HTML 語意化、CSS 響應式排版（mobile-first）、JS 基礎互動（DOM、事件、表單驗證），做出一個零依賴、`file://` 可直接開啟的靜態頁面。
- **痛點入口**：沒有「上一階段」，Stage 1 是全課程的起點，直接建立整個課程共用的品牌視覺語言與商品資料。
- **新概念清單**：語意化標籤、CSS 自訂屬性（design tokens）、mobile-first 疊加式響應式、accordion／倒數計時器等純 JS 互動、a11y 基礎（`aria-*`、focus 樣式、對比比率）。
- **刻意不教什麼**：多頁導覽（留給 stage2）、跨頁共享狀態（留給 stage3）、任何形式的資料持久化（留給 stage4）。

### Stage 2 — 多頁式靜態網站（WEB-14）

- **教學目標**：資訊架構與網站地圖、共用元件（JS fetch include）、自建輕量 UI 套件、跨瀏覽器相容性、SEO 基礎。
- **痛點入口**：Stage 1 只有一頁，不會遇到「同一段 header/footer 要在很多頁面各複製一份」的維護問題；Stage 2 一旦擴增到 10 個頁面，這個問題立刻浮現，因此引入 `partials/` + `js/include.js` 的 fetch include 機制。
- **新概念清單**：URL 命名與網站地圖、`sitemap.xml`／`robots.txt`、fetch include 共用導覽、design tokens 抽成獨立 UI 套件、麵包屑、更完整的表單驗證（欄位級錯誤訊息）、caniuse 查法與 graceful degradation。
- **刻意不教什麼**：任何前端框架（留給 stage3）、跨頁共享的「狀態」（例如購物車數量）——本階段的頁面之間仍然是各自獨立的 document，沒有真正的跨頁狀態同步機制。

### Stage 3 — 互動式動態網頁·純前端（WEB-15）

- **教學目標**：前端框架（React + Vite）、元件化、跨頁共享狀態管理（Context + useReducer）、第三方 API 串接與錯誤處理、SPA 路由。
- **痛點入口**：Stage 2 每頁都是獨立 document，換頁等於整份重新載入，前一頁 JS 裡的變數全部歸零——這讓「購物車」這種需要跨頁即時同步、頻繁變化的狀態幾乎無法用純 HTML/JS 乾淨地實作。
- **新概念清單**：JSX／元件／props、react-router-dom（動態路由參數、query string）、Context + useReducer 集中式狀態、`localStorage` 持久化、第三方 API 的 loading／成功／失敗三態處理與 fallback 策略、Vitest + Testing Library 元件測試。
- **刻意不教什麼**：任何後端／資料庫（本階段商品資料仍是打包進前端的靜態 JSON，購物車與訂單存在使用者自己瀏覽器的 `localStorage`，換裝置就看不到）、真實付款（留給 stage5）、伺服器端庫存管理（留給 stage4）。

### Stage 4 — 互動式動態網頁·後端（WEB-16）

- **教學目標**：RESTful API 設計、資料庫 schema 設計、認證與授權（bcrypt + JWT）、並發安全（條件式 UPDATE 防超賣）、前端串接真實後端。
- **痛點入口**：Stage 3 README 自己點出的限制——「換一台裝置看不到自己的購物車與訂單、沒有真正的庫存管理（兩人同時搶購同一件商品，彼此看不到對方的操作）、也沒有真正的付款」。這些問題本質上都需要一個共享的、真實的資料層才能解決。
- **新概念清單**：FastAPI 路由設計、SQLite schema（外鍵、UNIQUE/CHECK 約束）、bcrypt 密碼雜湊、JWT 簽發與驗證、`Depends()` 依賴注入、條件式 SQL UPDATE 防止 race condition、Vite proxy vs CORS、pytest + `TestClient`。
- **刻意不教什麼**：付款流程（`orders.status` 只有 `pending` 一種值，建單當下直接扣庫存，沒有「付款成功才算數」的中間狀態）、管理後台（商品只能透過種子腳本手動維護）、角色權限（所有使用者一視同仁），這些留給 stage5。

### Stage 5 — 完整應用系統·前台＋後台（WEB-17）

- **教學目標**：訂單狀態機設計、付款流程與交易一致性、角色權限（RBAC）、軟刪除與資料保護、後台聚合查詢、多應用前端架構。
- **痛點入口**：Stage 4 README「教學簡化聲明」點名的兩個限制——「沒有付款/金流」「沒有管理後台，商品資料只能透過 `seed_products.json` 手動維護」。本階段把這兩塊都補上，同時因為有了「付款」這個獨立事件，連帶把扣庫存的時機從「建單當下」改成「付款成功那一刻」。
- **新概念清單**：有限狀態機（合法/非法轉移驗證）、模擬金流、建單與付款分離、`role` 欄位與 `require_admin` 依賴注入疊加、401 vs 403 語意區分、`is_active` 軟刪除、SQL 聚合（`SUM`／`COUNT`）取代前端重算、獨立的 Vite admin app 與雙 SPA fallback。
- **刻意不教什麼**：即時通訊（後台看新訂單要手動重新整理）、任何效能調校（沒有索引優化、沒有快取、沒有壓縮）、壓力測試，這些留給 stage6。

### Stage 6 — 進階版·即時通訊/效能/壓測（WEB-18）

- **教學目標**：WebSocket 連線管理、SSE 串流回應、資料庫索引與 `EXPLAIN QUERY PLAN`、N+1 查詢修復、TTL 快取與 cache invalidation、HTTP 回應壓縮、併發與執行緒安全、壓力測試方法論、CI/CD 基礎概念。
- **痛點入口**：Stage 5 後台要看新訂單只能手動重新整理頁面；隨著資料量與流量增加，`products` 表沒有索引、後台訂單列表是 N+1 查詢、商品列表沒有快取——這些在小資料量下看不出問題，必須靠真實壓力測試才量得出差異。
- **新概念清單**：`ConnectionManager` 自寫連線管理、前端 exponential backoff 斷線重連、`async generator` + `StreamingResponse`、複合索引、單次 JOIN 取代逐筆查詢、TTL 快取、`GZipMiddleware`、SQLite 跨執行緒限制（`check_same_thread=False`）、locust 混合場景壓測、GitHub Actions CI 教材。
- **刻意不教什麼**：真正的雲端部署與 CD（`ci/github-actions-ci.yml` 只做到 build + test）、多 worker／多 instance 下的狀態同步（Redis Pub/Sub，留給延伸挑戰）、真實 LLM 客服（規則式 FAQ 比對），這些明確標示為「本課程刻意不實作」或留給延伸挑戰，不是六階段之後的下一步官方規劃。

## 3. 級別與點數對應說明

| 課綱代號 | 級別 | 點數 | 級別意義 |
|---|---|---|---|
| WEB-13（Stage 1） | A | 2 | 入門可上手：零依賴、單一技術棧（HTML/CSS/JS），適合完全新手 |
| WEB-14（Stage 2） | B | 3 | 可接案基礎：多頁資訊架構、共用元件取捨，開始需要工程判斷 |
| WEB-15（Stage 3） | B | 4 | 可接案基礎：引入前端框架與狀態管理，複雜度明顯提升但仍是純前端 |
| WEB-16（Stage 4） | C | 4 | 完整系統能力：第一次出現真正的後端、資料庫、認證授權 |
| WEB-17（Stage 5） | C | 5 | 完整系統能力：前台＋後台雙應用、狀態機、付款流程、角色權限 |
| WEB-18（Stage 6） | C | 5 | 完整系統能力：進階套件（WebSocket/SSE）、效能調校、壓力測試、CI 概念 |

點數反映的是**工作量權重**，不是單純的難度分級——Stage 3（B/4）點數與 Stage 4（C/4）相同，但級別不同，因為 Stage 4 首次跨入「後端系統設計」的能力範疇（C 級），即使兩階段的實作工作量接近。Stage 5、Stage 6 點數同為 5，是六階段中工作量最大的兩階段：Stage 5 因為要同時維護前台／後台兩個獨立前端應用＋更複雜的資料模型（狀態機、付款、角色），Stage 6 因為新增的技術主題數量多（WebSocket、SSE、四項效能調校、壓力測試、CI）且每項都要求有實跑證據。

## 4. 帶課建議

> 以下課時為**自估建議值**，不是官方規定的時數，實際應依學員程度、是否需要額外講解前置知識（例如完全沒碰過 Python 或 JavaScript）彈性增減。

| 階段 | 建議課時（自估） | 驗收方式 | 常見卡點 |
|---|---|---|---|
| Stage 1 | 3-4 小時 | 對照該階段 README 的「驗收清單」逐項勾選；重點檢查三個裝置寬度（<768px／768-1023px／≥1024px）版面是否切換正確 | 忘記 mobile-first 的疊加順序（`@media (min-width: ...)` 寫反）；`aria-expanded` 狀態與實際顯示狀態不同步 |
| Stage 2 | 4-6 小時 | 對照該階段 README 的「驗收清單」；用 `check-links.py` 檢查連結完整性，用逐頁 `curl` 檢查 200 | 忘記本階段**不能**用 `file://` 直接開啟（fetch include 在 `file://` 協定下會被瀏覽器擋掉），必須用 `python3 -m http.server` |
| Stage 3 | 8-10 小時 | 對照該階段 README 的「驗收清單」；`npm test -- --run` 全綠、`npm run build` 成功 | Context Provider 疊放順序錯誤（`ExchangeRateProvider`／`CartProvider` 要在 `App` 之外才能讓所有頁面共用狀態）；忘記匯率 API 失敗時要有 fallback，測試時打真網路而非 mock fetch |
| Stage 4 | 10-12 小時 | 對照該階段 README 的「驗收清單」；後端 `pytest -q`、前端 `npm test -- --run` 全綠；手動走一次「註冊→登入→加購物車→建單」流程 | 前後端分離開發時忘記啟動其中一個 process（Vite proxy 轉發會失敗）；`SECRET_KEY` 沿用開發預設值就部署；沒理解「快照庫存」跟「即時查詢」的差異 |
| Stage 5 | 12-16 小時 | 對照該階段 README 的「驗收清單」；後端／前台／後台三邊測試全綠；用測試帳號表格的 admin／customer 帳號各走一次流程 | 忘記後台是獨立的 Vite app，要多開一個終端機、路徑要帶 `/admin/`；搞混 401（沒登入）跟 403（登入了但沒權限）；忘記付款成功才扣庫存、建單當下不扣 |
| Stage 6 | 12-16 小時 | 對照該階段 README 的「驗收清單」；後端／前台／後台測試全綠；跑一次 `loadtest/asyncio_load_test.py` 煙囪測試確認腳本能動 | WebSocket 認證用 query string 而非 header（瀏覽器原生 API 限制，不是忘記加）；忘記 `async def` 路由裡忘記 `await`；混淆「索引存在」與「索引真的被用到」（要看 `EXPLAIN QUERY PLAN`，不是看 schema 有寫就假設有效） |

## 5. 全課程刻意簡化總表

> 各階段獨立的完整聲明見各自 README 的「教學簡化聲明」一節；以下是跨階段彙整版，方便一次看完整課程的取捨與「真實產品該怎麼做」的對照。

| 階段 | 教學簡化之處 | 真實產品該怎麼做 |
|---|---|---|
| Stage 1 | 訂閱表單是純前端 mock，填了不會真的送出或儲存 | 需要一支後端 API 接收表單、寄送確認信或寫入資料庫 |
| Stage 1 | 招牌選品純展示，沒有購買功能 | 購物車與下單需要前端框架的狀態管理＋後端庫存/訂單 API |
| Stage 1 | 門市地圖是手繪 SVG 示意圖，非真實地圖 | 正式產品通常嵌入 Google Maps 等地圖服務的 iframe |
| Stage 2 | 聯絡表單是 mock，沒有後端接收或儲存 | 需要 stage4 等級的後端 API 才能真正收信/存資料 |
| Stage 2 | 只有 3 個商品詳情頁示範，其餘 9 筆只在型錄呈現基本資訊 | 正式產品需要每筆商品都有獨立詳情頁，通常改用模板/CMS 動態產生而非手寫 HTML |
| Stage 2 | `sitemap.xml`／canonical 用 RFC 2606 保留的範例網域 | 上線前必須換成實際網域 |
| Stage 3 | 沒有後端，結帳「送出訂單」只是存進 `localStorage` | 真實電商至少需要後端驗證庫存與價格（不能只信任前端傳來的金額）、真正的金流串接 |
| Stage 3 | 庫存是加入購物車當下的快照，不是即時查詢 | 有後端與多人同時操作後，庫存上限必須即時向後端查詢 |
| Stage 3 | 訂單編號用 `Math.random()` 產生，不保證全域唯一 | 真實後端會用資料庫自增 ID 或 UUID |
| Stage 4 | 沒有付款/金流，建單當下直接扣庫存 | 需要金流串接、webhook 回呼確認付款狀態後才扣庫存 |
| Stage 4 | 沒有 Repository Pattern（資料層沒有抽象介面） | 本課程六階段永遠只用 SQLite；若需要支援多種資料庫後端，應加上抽象層（可參考姊妹教材 meowshop-tutorial 的做法） |
| Stage 4 | 購物車沒有樂觀更新，每次操作都要等後端回應 | 正式產品通常會做樂觀更新，先假設成功、失敗再復原並提示錯誤 |
| Stage 4 | 關鍵字搜尋沒有 debounce，每個字都立刻打一次 API | 正式產品通常加上防抖動處理減少不必要的請求量 |
| Stage 5 | 付款是完全模擬的金流，只判斷卡號字串 | 需要接上真實金流服務（如 PayUNI、Stripe），並處理簽章驗證與非同步 webhook 回呼 |
| Stage 5 | 取消已付款訂單不處理退款 | 接上真實金流後，取消已付款訂單必須同時呼叫退款 API |
| Stage 5 | 建單不預留庫存，一直要到付款那一刻才會發現庫存不夠 | 正式產品常見做法是「建單先鎖庫存一段時間、超時自動釋放」 |
| Stage 5 | 會員清單唯讀，沒有停用/刪除功能 | 需要加上帳號停用欄位與對應的登入錯誤處理 |
| Stage 5 | 後台清單沒有分頁，一次全部撈出來 | 資料量大時需要加上 `limit`/`offset` 或游標分頁 |
| Stage 6 | 客服助理是規則式 FAQ 比對，不是真的 AI | 真實產品這裡通常接 LLM streaming API，介面（SSE 逐字送出文字）長得完全一樣 |
| Stage 6 | 快取／WebSocket 連線清單只存在單一 process 記憶體，不支援多 worker | 多 instance 情境需要引入 Redis Pub/Sub 之類的外部共享狀態 |
| Stage 6 | CI 只做到 build + test，deploy 留白 | 需要一個實際存在的雲端部署目標（Cloud Run、Render 等）才能接上真正的 CD |
| Stage 6 | 壓力測試數字只在本機環境下有意義 | 正式環境的容量規劃需要在目標部署環境實測，不能直接套用本機數字 |

（跨階段共同的簡化：`SECRET_KEY` 開發預設值是固定字串，`.env.example` 內附產生隨機字串的指令，正式部署前必須更換——stage4/5/6 皆同。）
